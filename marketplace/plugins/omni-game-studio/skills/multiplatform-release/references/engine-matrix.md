# 三引擎能力矩阵与选型方法

> ⚠️ **所有"支持 / 不支持"结论都必须带引擎版本，并在使用前按官方文档复核。** 三引擎的平台支持每年都在变，本文件给的是判断框架与方向，不是永久事实。
>
> 本矩阵仅覆盖 Cocos Creator / Unity / Godot。**Unreal Engine 5 不在本表内**：其平台支持由 `unreal-engineer` 按 UE 大版本 + 目标平台单独评估，并以 Epic 官方文档核实，不套用下表的三引擎结论。

## 一、选型方法：五维矩阵

选型不是选"最好的引擎"，是选"在这个项目约束下返工最少的引擎"。按五维打分（1–5 分，5 最优），加权后给结论，**并必须写出"结论会反转的条件"**。

| 维度 | 权重建议 | 判断依据 |
|------|---------|---------|
| 目标平台支持度 | 30% | 首发平台是否有原生构建路径；需要转换工具链的平台，包体与性能损耗能否接受 |
| 包体与性能天花板 | 25% | 首包能否压进平台上限；目标机型下限能否稳住帧率 |
| 团队技能栈 | 20% | 现有成员会什么；学习成本折算成工期 |
| 生态与三方 SDK | 15% | 支付、广告、统计、推送、登录、语音、云存档是否有成熟方案 |
| 授权与长期成本 | 10% | 授权费、分成、源码可控性、长期维护风险 |

**输出格式（必须包含"反转条件"）**：

```
| 维度 | 权重 | Cocos Creator | Unity | Godot |
| 加权总分 | 100% | x.x | x.x | x.x |

结论：推荐 X
反转条件：若 <条件 A> 成立，则结论变为 Y；若 <条件 B> 成立，则三引擎均不适用，需 <替代方案>
```

## 二、三引擎逐项对比

| 维度 | Cocos Creator 3.x | Unity | Godot 4.x |
|------|-------------------|-------|-----------|
| 主语言 | TypeScript | C# | GDScript / C# |
| 授权 | 免费（引擎开源，编辑器免费） | 按营收档位收费，政策有调整历史，**用前必须核实当前条款** | MIT，完全免费开源 |
| 2D 能力 | 强（组件式，适合 2D 与轻量 3D） | 中（2D 基于 3D 管线，需额外调优） | 强（2D 是独立管线，节点组合灵活） |
| 3D 能力 | 中（轻中度够用，重度需评估） | 强（URP / HDRP，生态最成熟） | 中（4.x 已可用，重度项目需评估） |
| 渲染管线 | 内置 forward，支持自定义 effect | 内置 + URP / HDRP | Forward+ / Mobile / Compatibility |
| 小游戏平台 | **原生构建目标**（微信 / 抖音 / 支付宝等） | 需 WebGL 转换工具链，包体与性能损耗需实测 | **无官方路径**，需第三方或自研 |
| Web | 支持（WebGL，WebGPU 视版本） | 支持 WebGL（移动浏览器性能弱） | 支持（WebGL2；C# 版本 Web 导出支持度需核实） |
| Android / iOS | 原生支持 | 原生支持（最成熟） | 支持 |
| HarmonyOS | 有构建目标（**版本相关，需核实**） | 官方 / 团结引擎路线（**需核实当前状态**） | **需核实**（社区方案为主） |
| Windows / Linux | 支持（Linux 支持度需核实） | 支持（含 IL2CPP） | 支持（导出模板需匹配版本） |
| 热更新 | 原生热更新方案 + 小游戏资源更新 | 需自行设计（IL2CPP 下不能下发可执行代码） | PCK 补丁机制，需自行设计分发 |
| 三方 SDK 生态 | 中等，国内小游戏 SDK 覆盖好 | 最全 | 较少，商业 SDK 常需自研桥接 |
| 调试与剖析 | 编辑器 Profiler + 浏览器工具 | Profiler / Frame Debugger / Memory Profiler（最强） | Monitor / Profiler（够用但较弱） |
| 学习曲线 | 低（前端背景上手快） | 中高 | 低中（GDScript 易学，C# 需 .NET 版） |

## 三、平台 × 引擎支持矩阵

图例：✅ 原生支持 ｜ ⚠️ 需工具链/插件，有损耗 ｜ ❓ 需按版本核实 ｜ ❌ 无可行路径

| 平台 | Cocos Creator | Unity | Godot |
|------|---------------|-------|-------|
| 微信小游戏 | ✅ | ⚠️ WebGL 转换 | ❌ / ⚠️ 第三方 |
| 抖音小游戏 | ✅ | ⚠️ WebGL 转换 | ❌ / ⚠️ 第三方 |
| Android | ✅ | ✅ | ✅ |
| iOS | ✅ | ✅ | ✅ |
| HarmonyOS | ❓ | ❓ | ❓ |
| Windows | ✅ | ✅ | ✅ |
| Web | ✅ | ✅ | ⚠️（C# 版需核实） |
| Linux | ❓ | ✅ | ✅ |

**使用规则**：
- 表里出现 ⚠️ 或 ❓ 的组合，方案里必须写"实测验证项"与"失败时的退路"
- 不允许把 ❓ 当 ✅ 用。用户问"能不能发鸿蒙"，正确回答是"当前引擎版本需要核实，核实方式是 XX，如果不支持则退路是 YY"

## 四、跨引擎迁移清点

被问"从 A 引擎迁到 B 引擎"时，必须按三类清点并给工作量占比，不能只说"建议迁移"。

| 资产类别 | 可复用 | 需改造 | 必须重写 |
|---------|--------|--------|---------|
| 美术原图 / 音频源文件 | ✅ 源文件 | 导入设置、压缩格式、图集划分 | — |
| UI 布局 | — | 布局思路与视觉稿 | UI 层级、锚点、适配逻辑基本重写 |
| 玩法逻辑 | — | 数据结构与公式 | 代码全量重写（语言与 API 都变） |
| 动画 | — | 关键帧数据（视格式） | 动画状态机、混合树 |
| 特效 / Shader | — | 效果意图 | 三引擎 Shader 语言互不兼容，基本重做 |
| 数值配置表 | ✅ 表结构 | 解析代码 | — |
| 存档格式 | — | 字段映射 | 序列化实现 |
| 平台 SDK 接入 | — | 业务逻辑 | 桥接层全量重写 |

**典型占比参考**（仅用于初期沟通，必须由工程师按实际项目复核）：美术音频源文件可复用度高；逻辑与 UI 通常占总工作量的 60% 以上；特效重做是常被低估的隐藏成本。

## 五、典型场景速查

| 场景 | 方向性建议 | 关键前提 |
|------|-----------|---------|
| 只发微信/抖音小游戏 | Cocos Creator | 首包预算能否满足 |
| 小游戏 + Steam 双发 | Cocos（小游戏）+ Unity/Godot（Steam）双工程，或 Unity 单工程 + 转换 | 双工程的维护成本 vs 转换后的性能损耗，需实测对比 |
| 3D 中重度、要上 PC/主机 | Unity | 授权成本与包体 |
| 2D 独立游戏、预算敏感、要上 PC | Godot | 目标平台导出成熟度与三方 SDK 需求 |
| 已有 Unity 项目要上小游戏 | 评估 WebGL 转换后的包体与帧率 | 转换后性能若不达标，退路是 Cocos 重做小游戏版 |
| 已有 Godot 项目要上小游戏 | 谨慎，需评估第三方方案可行性 | 无官方路径，可能需重做 |
| 团队只有前端背景 | Cocos Creator（TypeScript） | 3D 重度需求可能不够 |
