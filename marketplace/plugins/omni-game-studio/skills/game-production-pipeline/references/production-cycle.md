# 游戏制作阶段、里程碑与 Sprint

适用于新项目、原型验证到上线运营。按团队规模缩减仪式，保留风险验证、真实可玩版本和明确验收责任。用户已有项目时从当前阶段接续，不要求重走已完成阶段。

## 五阶段与现有文档的对应

| 制作阶段 | 目标与主要活动 | 现有产出 |
|---|---|---|
| 立项与概念 | 验证目标玩家、核心体验、市场依据、范围、预算和团队能力，决定 Go / No-Go | docs/00-brief.md、docs/01-gdd.md |
| 预制作 | 验证核心玩法原型；制作小而完整、接近目标品质的垂直切片；确定引擎、工具链、资源规格和制作流程 | docs/02-tech.md、docs/03-art.md、docs/04-audio.md、原型与垂直切片 |
| 批量制作 | 程序、美术、策划和音频按优先级并行；逐 Sprint 集成成可玩版本、评审并重排 backlog | GDD、技术与资源文档、Sprint 计划及复盘 |
| 测试与打磨 | 从 Alpha 功能完整，推进到 Beta 内容锁定，再到可发行的 Gold；做回归、兼容、性能、平衡和本地化 | docs/05-qa.md、docs/06-release.md、测试与构建证据 |
| 发布与运营 | 排期、送审、发行；上线后监控、热修复、更新、活动及玩家反馈 | docs/06-release.md、运营复盘和后续版本 backlog |

插件原有 brief → gdd → tech → art → audio → qa → release 是文档与工件子门禁，不等同于上述制作里程碑。一个制作阶段可能跨越数个文档门禁和多轮 Sprint。

## 里程碑门禁

项目启动时，将通过条件、评审人和证据路径填写到 docs/09-milestones.md。未达标时记录风险与修订计划；不以状态脚本显示通过作为实际交付证据。

| 门禁 | 通过需要评审的内容 |
|---|---|
| G1 立项 | 目标玩家与核心循环清楚；范围、风险、预算及“不做什么”明确；负责人接受 Go / No-Go 决定 |
| G2 预制作 | 原型实际验证核心玩法假设；垂直切片证明玩法、美术、音频和技术管线可以集成并达成约定品质、性能与制作成本 |
| G3 Alpha | 约定功能完整且有集成构建；主要流程可运行；阻塞项、稳定性和剩余工作有负责人 |
| G4 Beta | 内容达到约定完整度并冻结新增功能；仅处理经评审的缺陷、平衡、本地化与兼容问题；发布及合规准备可追踪 |
| G5 Gold / Release | 候选包经过目标平台检查、回归和发行负责人签署；送审、上线、回滚及监控责任明确 |
| Live Ops | 有线上指标和问题监控、热修复流程、支持责任与下一版本的优先级依据 |

如决定解除 Beta 功能冻结或重开已通过的门禁，必须说明影响的工期、风险和重新验收范围，并重新记录决议。

## Sprint 循环

一般 2–4 周一个 Sprint；独立开发者可用更短周期。以团队能稳定集成和评审为准，避免把周期本身当作交付目标。

1. 从 roadmap 和当前 backlog 选出一个可验收 Sprint 目标，列出策划、程序、美术和音频需要交付的工作及依赖。
2. 开始前写明范围、负责人、完成定义、目标平台和最小集成版本；超出能力的工作不算承诺。
3. 持续集成各职能产出。结束时演示或记录一个真实可玩的构建，执行该 Sprint 约定的测试并登记缺陷。
4. 评审玩家/团队反馈，复盘完成情况和阻塞原因，按风险重排下一轮 backlog。避免用任务完成数替代可玩版本与验收结果。

如果构建或验证失败，记录日志、影响和修复负责人；如确实没有可玩构建，明确写未交付及原因，不要将 Sprint 标记为通过。

## 按团队规模裁剪

- 独立开发或小团队可由一个人兼任多职，保留简短立项、可玩原型、垂直切片和真实构建；减少文档和会议。
- 多团队项目增加每个门禁的评审人、外部依赖、变更记录、资产接入规范和构建产物责任。
- 任一规模都应在预制作验证产能后再确认批量制作排期；不根据未验证的 demo 假定量产速率。

工具选型遵从团队现有系统；模板只提供本地可读的记录格式，不要求 Jira、某云服务或特定 CI 产品。

## 证据边界

omni_state.py 只验证阶段文档存在、标题及 TODO，不检查这些里程碑的真实内容。文档记录的构建、测试、玩家反馈或审批都需要人工或对应工具实际完成；状态字段本身不能替代验证。
